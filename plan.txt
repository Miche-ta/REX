REX-MUSIC: PLAN TO MAKE IT PERFECT FOR AUDIOPHILES
===================================================

Each phase has an exit test, so we know when it is actually done.
Estimates (judgment, not measurements): about 70% as a daily player for the owner,
about 45-50% as a polished app other people could install.


PHASE 0: PROVE WHAT EXISTS  [DONE: real-app run incl. lyrics, fake-card test passes]
------------------------------------------
- Run everything in the real app, with the DAC and the Terminal tab open.
- Run the fake-card test:   sudo modprobe snd-dummy
                            cd src-tauri && cargo test dummy_card -- --ignored --nocapture
  and fix what it finds.
- Commit and tag a baseline.
- Try the new Output-tab options: buffer/period size, mixer control picker,
  "Card release: D-Bus (experimental)", Kernel hw_params, Copy report (Terminal tab).
EXIT: a full album plays gaplessly, every view works, no errors in the Terminal tab.


PHASE 1: TRUST (RELIABILITY)
----------------------------
1. [IMPLEMENTED, passes the fake-card tests, needs a real-DAC listening test]
   Two-thread audio pipeline: one thread decodes ahead into a bounded buffer, another
   feeds the sound card. Needs track-boundary markers in the buffer (so rate changes and
   the position clock are handled), raw i32 samples (never f32, to stay bit-perfect), a
   flush on seek/skip, real-time priority for the writer, underrun counters.
2. Gapless across sample-rate and format changes: drain, reopen, verify the DAC clock has
   settled before the next track starts.
3. USB freeze investigation (Intel xHCI "not part of TD" errors): use the period/buffer
   settings and the diagnostics report to isolate the cause; document working settings.
4. Device hot-plug: handle the DAC unplugging and replugging without a restart and
   re-select it automatically.
As built (src-tauri/src/pipeline.rs): decoder thread queues ~1 s ahead through one ordered queue; the
writer thread owns the card, keeps the clock/VU, and switches the UI's track info only when the new track
is audible. Seek/skip clear the queue. The card stays open ~1.5 s after the last track, then goes back to
PipeWire. Not done yet: real-time priority for the writer thread (needs RTKit or rlimits).
Rollback point: git tag pre-pipeline.
EXIT: 8 hours of playback with no freeze and zero unexplained underruns.


PHASE 2: VISUALS AND LYRICS
---------------------------
(Reconsidered: both are worth doing if built safely and after the pipeline.)

2a. Online lyrics (independent of the engine)   [IMPLEMENTED, needs a real-app test]
- OFF by default: the Lyrics tab shows a "Fetch online" button when no local .lrc or tag
  lyrics exist; a setting turns on automatic fetching.
- Source: LRCLIB (free community service, no account or key, synced lyrics).
- It sends title, artist, album and length to a third party, so it must be opt-in.
- Cache results on disk in the cache folder (never in the music folders): each song is
  fetched once. Short timeout; no error when offline; fall back to local lyrics.
- One new dependency for HTTP requests (ureq).
- As built: Lyrics tab footer has "Fetch online" and "Auto-fetch: off|on"; lookup order is
  .lrc file, embedded tags, local cache, then (only if asked/auto) lrclib.net /api/get with a
  /api/search fallback; "not found" is cached too, network errors are not.

2b. Visualizers beyond the VU meter (after Phase 1 item 1)
- The decode thread (not the thread feeding the DAC) computes the data, so the audio path
  is never slowed. Publish a small snapshot ~30 times a second: 32 frequency bands and
  ~256 waveform points per channel; the page reads it by command or event.
- Delay the picture by the buffer length so it matches what is heard.
- Use rustfft; one FFT per chunk.
- Order of value: (1) spectrum bars, (2) true-peak and RMS meters, (3) phase scope
  (goniometer), (4) spectrogram (optional). All go in the Now playing tab strip next to
  Art, VU Meter and Lyrics, in the existing flat instrument style.
EXIT: lyrics fetch once and are cached; visualizers run with no change in underrun count.


PHASE 3: THE AUDIOPHILE FEATURE SET
-----------------------------------
1. CUE sheets (single-file album rips) with sample-accurate track boundaries.
2. DSD (native and DoP): only if the owner has DSD files and a DAC that plays them.
3. Bit-perfect proof: a "verify" mode comparing what was decoded with what reached the
   card, plus an honest note when the DAC's volume control is digital.
4. Hardware controls: DAC filter and other ALSA switches shown in the Output tab (the
   mixer picker already exists).
5. Optional processing, clearly separated: EQ or room correction behind a switch that
   visibly turns the "bit-perfect" indicator off.
EXIT: a CUE+FLAC rip and a DSD file both play correctly.


PHASE 4: A LIBRARY WORTH LIVING IN
----------------------------------
1. Background, non-blocking scans with progress and cancel. (The on-disk cache with
   incremental rescans already exists.)
2. Album/artist browser, album-level ReplayGain, tag editing.
3. Queue and position restored on launch: paused, never auto-playing.
4. Playlist import/export (.m3u8 with relative paths).
EXIT: a 20,000-track library scrolls smoothly and rescans in seconds.


PHASE 5: SHIP IT
----------------
1. First-run setup: pick the music folder, pick the DAC, explain the PipeWire hand-off.
2. Packaging: AppImage plus an Arch package, with a documented install.
3. Accessibility pass, a settings page, a proper README with screenshots.
4. Crash reports through the diagnostics export.
EXIT: a stranger installs it and gets bit-perfect output in under five minutes.


ORDER OF WORK
-------------
Phase 0, Phase 1, then Phase 2a (online lyrics, can start any time), Phase 2b after the
pipeline, then CUE (Phase 3), the library work (Phase 4), and shipping (Phase 5).
DSD and the optional-processing items come last: they matter to fewer people.
